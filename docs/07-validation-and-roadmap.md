# 07 验证与重构路线

更新：2026-10-06。状态：重构路线草案。

目标是验证“朋友通过网页可以稳定玩完一局”，而不是恢复旧功能清单或先完成视觉换皮。

## 阶段 0：可恢复的文档基线

- 已完成：建立旧实现的归档提交与标签，保留参考素材和本地配置，移除旧实现。
- 已完成：整理产品、规则、流程、UX、素材、网页版边界与验证文档草案。
- 待完成：审阅 [规则决策表](02-rules-and-decisions.md)，选定首发板子与核心分支。

本阶段的文档不是已通过用户实测的产品规格。新功能开发开始前，应明确哪些草案采用为基线，哪些继续保留为待决项。

## 阶段 1：桌边体验与声音可行性

交付入口、大厅、身份查看、夜晚行动、狼人协作、公共主持、白天录入和结束页的线框或可操作原型。

使用实际 iOS Safari 和 Android Chrome 验证用户启用音频、连续指令、失败恢复及前台切换。允许文字主持，测试失去声音时全桌是否知道如何继续。

进入下一阶段的条件：至少一组目标用户能理解入场与一夜流程，行动与公共播报不会互相干扰，隐私布局没有明显身份提示，网页版音频边界可接受。

## 阶段 2：唯一规则核心与对局事实

交付选定规则包的配置校验、随机发牌、行动权限、统一结算、死亡反应、及时判胜及可恢复的对局事实。

优先验证规则组合和信息边界，再接入界面。已有旧测试只作为场景来源；固定身份顺序、公开跳过死亡角色、漏掉猎人放弃等行为不能因旧测试通过而成为新要求。

进入下一阶段的条件：同一批动作的结果不依赖到达顺序，重复操作不产生额外影响，隐私视角正确，规则决策表中的已选分支都有验证。

## 阶段 3：网页版完整对局

交付首发板子的完整一局、公共音频或文字主持、刷新恢复、短时断线、暂停接管、白天更正、局后结果和保留席位的下一局。

进入实测的条件：不同浏览器共享同一事实，一台设备异常不会静默改变行动或卡死，结束后不会把旧身份、资源或音频队列带到下一局。

## 阶段 4：真实聚会验证与首发

建议完成 3 至 5 场八人线下测试，混合 iPhone 和 Android 浏览器，至少轮换两名房主与两台公共播报设备。其他人数和守卫、猎人板子另有测试记录后再加入推荐列表。

| 场景 | 应观察的结果 |
| --- | --- |
| 首次加入、重开、席位变化 | 身份与座位准确；没有重复入座或重复发牌 |
| 狼人分歧、队友短时失联 | 有规则允许的处理方式，公共提示不泄露角色 |
| 女巫放弃、药剂耗尽、守卫限制 | 所有合法与非法行动有确定结果 |
| 夜晚和白天猎人死亡、放弃开枪 | 反应不会漏掉或卡住，判胜等待完整反应结束 |
| 夜晚已经满足胜负条件 | 不额外要求白天再投一次才结束 |
| 刷新、网络中断、公共页离开前台 | 能恢复当前事实，没有重复消费资源或补播旧台词 |
| 音频受阻、声音缺失、文字主持 | 用户能理解暂停与降级，动作点击不被吞掉 |
| 房主出局或离线 | 出局不影响组织权限，接管不开放全员身份 |
| 无人出局、平票线下处理、误录 | 录入明确，更正边界可信，系统不代替线下投票 |
| 局后与下一局 | 胜负可解释，信息按政策公开，新局与旧局隔离 |

## 体验指标与记录

记录邀请到就绪时间、整桌准备时间、正常白天录入之外的维护次数、卡住时间、误点、音频恢复次数和再次开局意愿。建议目标见 [01](01-product-requirements.md)，实际结果与设备、浏览器版本一起保存。

可以在真实游戏前用简短测试模式演练指令与恢复，但不能让演练身份或动作进入正式对局。

## 发布与后续

首发只承诺验证过的板子、规则和浏览器条件。素材润色、更多人数、安装增强和环境音在核心指标达标后推进。原生 App 不属于这条路线。

当前为文档与素材重置阶段，没有应用构建或运行测试可执行。本轮验收是归档可恢复、旧实现移除、素材完整、文档链接正确及范围一致。
